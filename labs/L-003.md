# L-003 · Issue, Cloud-PR und Peer-Review

**40 Minuten, Zweierteams mit Partnerteam.** Grundlage ist der integrierte M-002-Stand oder das bereitgestellte `m002`-Repo. Der Feature-PR bleibt für L-004 geöffnet.

## 0–7 Min · Issue mit Abnahmekriterien

Lesen Sie `docs/issues/ISSUE-02-semver.md` und erstellen oder öffnen Sie das zugehörige GitHub-Issue. Klären Sie die Reihenfolge Breaking Change, Feature, Fix/Perf und unverändert. Prüfen Sie die Ausgabe auf stderr und halten Sie einen eigenen Grenzfall fest, etwa ausschließlich `perf`, leere Eingabe oder die Kursregel für `0.x`.

## 7–20 Min · Agent beauftragen und PR einsehen

Wählen Sie Repo und grünen Basisbranch in Cursor Web. Geben Sie Issue-Link, Kriterien, erlaubten Umfang und Testbefehle an. Lassen Sie den Agenten einen Arbeitsbranch und PR gegen `main` erstellen. Bei fehlender PR-Erstellung öffnen Sie ihn manuell. Prüfen Sie Head, Base, Diff und aktive SemVer-Tests. Nach erster Prüfung kann der Autor den Draft als Ready markieren.

**Prompthilfe.** „Setze [Issue-URL] auf einem Arbeitsbranch um. Erhalte bestehendes CLI-Verhalten und Abhängigkeiten. Aktiviere ausschließlich den Skip für ISSUE-02 und führe Zieltests und Gesamtsuite aus. Öffne einen PR gegen main. Fasse Prüfungen und Grenzen zusammen. Kein Merge.“

## 20–30 Min · Unabhängiges Review

Tauschen Sie die PRs. Prüfen Sie **Files changed** und **Checks** sowie die fachliche Anforderung. Reproduzieren Sie mindestens einen Randfall außerhalb der vorhandenen Testkombinationen. Ein Fall mit nur `perf` soll von `2.3.1` auf `2.3.2` erhöhen. Schreiben Sie einen konkreten Kommentar mit Stelle, Repro, Soll und Ist. Bei einem blockierenden Befund **Request changes** verwenden, sofern Rolle und Repo das erlauben. Bugbot kann zusätzliche Hinweise liefern. Das Partnerteam prüft deren Relevanz.

Wenn der Live-PR den Randfall bereits korrekt behandelt, bearbeiten Sie die Korrekturschleife am bereitgestellten Trainings-PR bzw. Diff `m003-review`. Einen künstlichen Befund im richtigen Live-PR vermeiden.

## 30–40 Min · Korrektur und erneute Prüfung

Geben Sie dem bestehenden Cloud-Lauf den belegten Befund, den PR-Link und Head-Branch. Fordern Sie die kleine Korrektur mit Regressionstest auf demselben Branch an. Alternativ beheben und pushen Sie lokal. Prüfen Sie den neuen Commit, Check und Review. Der Reviewer bestätigt erst nach eigener Gegenprobe und kennzeichnet ausstehende Checks. Halten Sie den PR für L-004 offen.

**Fallback.** Wenn bis Minute 20 kein prüfbarer Diff vorliegt, arbeiten Sie am vorbereiteten `m003-review`-Stand. Ohne GitHub formulieren Sie den Kommentar an einer Diff-Zeile und prüfen den korrigierten Patch lokal. Dokumentieren Sie, welche GitHub-Nachweise fehlen.
